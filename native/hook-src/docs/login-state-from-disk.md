# 登录态判定：改用磁盘信号，实测可用

## 结论先说

**`op 7` 第一次报出真实 uin，而且可复现。**

| 阶段 | `op 7` 回报 |
|---|---|
| QQ 停在登录页 | `status=0 flags=0x0 value0=0` |
| 点击"登录"后 3~8 秒 | `status=1 flags=0x4 value0=3083456343` |
| 重启 QQ 后再看 | 复位为 `status=0`，再点击又变 `status=1` |

两轮完整周期，均正确。QQ 持续运行 66 秒、96 线程、无崩溃。

## 但这**不是** hook 的成功

必须区分清楚：

- 原目标"**通过 hook 观测 QQ 内部真实登录事件**"——**五次尝试全部失败**，
  详见 `observer-not-firing.md`。
- 现在达成的是"**产品上能正确报告登录账号**"——**换了判定方法**。

原因很直白：QQ 自己就把答案写在磁盘上，而且不需要任何内部知识。

## 磁盘上到底有什么

```
<HOME>/.config/QQ/auth/login.enc          415B，每次登录被重写
<HOME>/.config/QQ/Partitions/qqnt_<uin>/  目录名里就是 uin（明文）
<HOME>/.config/QQ/Partitions/qq-browser_<uin>/
```

容器实测（`HOME=/app`）：

- 01:32 点击登录 → `qqnt_3083456343` mtime = 01:32
- 01:43 再次登录 → `login.enc` mtime = 01:43:18
- 01:57 再次登录 → `login.enc` mtime = 01:57:21

时间戳与按钮点击时刻一一对应，误差 1 秒内。

## 三个必须记住的判据错误

这些都是实测踩出来的，每一个都会给出"看起来很合理"的错答案。

### ① "目录存在" ≠ "已登录"

`qqnt_3083456343` 是**持久化**的，登录前就存在、登录后 mtime 也不变。
拿它当触发器，会在 QQ 停在登录页时报告已登录 —— 假阳性。

### ② "文件存在/较新" ≠ "刚登录"

第一版把 `login.enc` 的存在当作依据，同样假阳性。
**只有"在我们开始观察之后被写入"才是登录事件。**
所以第一帧只记基线，之后每次变化才算一次登录。

### ③ `readdir` 取第一个匹配 → 账号取错

容器里 `Partitions/` 下同时有 `qqnt_9210`、`qqnt_9211` 和真正的
`qqnt_3083456343`。`readdir` 顺序任意，取第一个匹配报了 **uin 9211**。
必须选**最近修改**的那个目录。

顺带一个纯 C 的坑：`g_login_uin` 原本是 `int`，3083456343 超过 2^31，
截断成负数后再按 `uint64` 发出，线上变成 `18446744072498040663`。
看起来像"垃圾 uin"，实际是符号扩展 —— 改成 `long long` 即对。

## 为什么这条路是对的

1. **不依赖 QQ 内部结构**。不 hook、不扫 vtable、不猜符号，QQ 升级不受影响。
2. **零风险**。只读文件系统，不往 QQ 进程写任何字节 —— 之前那些崩溃全部消失。
3. **可验证**。文件 mtime 能与操作时刻对齐，比"hits 非零"更容易确认。
4. **符合既定分工**。判定登录态属于**策略层**（本该在 TS/Node 侧），
   而策略不该依赖二进制内部布局。机制层（ptrace、注入、relay）保留原样。

## 实现位置

载荷 `test/payload.cc` 里 `login_dir_main` 线程：

- 每 2 秒：扫 `Partitions/` 找 `qqnt_<digits>`，取 mtime 最新的作为 `uin`
- 每 2 秒：`stat(auth/login.enc)`，与上次比
- 首帧只记基线；之后的任何变化 → `do_announce_login(uin)` → 推 `op 7`

hook 代码**保留但不默认安装**：机制已验证正确，是研究资产；
生产判定路径不再依赖它。

## 仍然没解决的

- **登出**检测不到。目前只有"登录"事件；登出只能靠目录消失/进程重启，
  未做验证。
- `op 7` 只报 uin，不报昵称、在线状态。
- 多账号切换未验证（只在单账号容器里测过）。

## 附：一个把"hook 崩溃"和"测试全红"连到一起的 bug

写完登录检测后回归测试，`slot_relay` 与 `vtable_inproc` 双双段错误，
**在任何输出之前就崩**（连 `relays live at start: 0` 都没打出来）。

### 根因：relay 的页是只读的

`slot_relay_install` 把 relay 所在的页设成：

```c
mprotect(mem, kPageSize, PROT_READ | PROT_EXEC);   // 缺 PROT_WRITE
```

而入口计数器的第一条指令就是 `incq 24(%r11)` —— **写同一页**。
只读页上写入 → 每次调用必崩。

**这一个 bug 同时解释了两件此前分开记录的事：**

1. 测试"无声段错误"（看起来像测试框架坏了）；
2. 实测里"注入装有函数 hook 的载荷后 QQ 反复崩溃"（看起来像容器不稳）。

之前我把后者归因于"缺重放桩"和"覆盖太短的函数"—— 那两个确实也是真 bug，
但**只读页这一条单独就足以让任何一次 relay 调用崩掉**。

### 顺带修掉的偏移错

`hits` 被硬编码成 `+32`，而结构体实际布局是
`slot(4) pad(4) original(8) observer(8) hits(24)` → **`+24`**。
写 `+32` 会越过结构体末尾，踩到同页的 trampoline。

现在加了 `static_assert` 锁死四个偏移，这类错编译期就会报。

### 教训

"测试框架坏了"和"代码坏了"看起来一模一样。这次是**禁用计数器做二分**
（`incq` 一注释掉，全部 4 个测试立刻通过）直接指出问题的，
比读代码快了太多。
