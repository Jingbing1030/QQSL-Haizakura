# メディア転送設定


## 動画アップロードの接続数

動画アップロードは既定で 1 接続を使用します。**設定 → 全体設定 → 動画アップロード
接続数**で、1、2、3、4 の中から接続数を選択してください。`config/snowluma.json` に
おける同等の設定は次のとおりです。

```json
{
  "videoUploadConcurrency": 1
}
```

この設定はすべてのアカウントに適用されます。WebUI からの保存は次回の動画
アップロードに反映され、すでに準備中または送信中のアップロードは元の値を保持します。
ファイルを手動で編集した場合は、Haizakura を再起動してください。古い構成で値が
欠けている場合は 1 接続とみなします。不正な値は報告され、丸め込まれることは
ありません。部分的な構成の保存および構成のバックアップでも、この設定は保持されます。

並列化が適用されるのは動画本体のみです。カバー、画像、ボイスメッセージ、ファイル
アップロードは既存の動作を維持します。2 MiB 以下の動画は引き続き 1 接続を
使用します。最後の動画チャンクは、先行するすべてのチャンクが確認されるまで待機します。
この設定は OneBot アクション、メッセージセグメント、レスポンスの形を変更しません。

中断された接続は、上限のある再試行予算の範囲内で、未確認のチャンクのみを再試行します。
既知のサーバーバックプレッシャーが発生した場合、そのアップロードは 1 つの有効な
リクエストに縮小され、遅延後に再試行されます。サーバーによる拒否、不正な確認応答、
再試行予算の枯渇はアップロードを失敗させます。失敗したアップロードが送信済みとして
暗黙に報告されることは決してありません。

デバッグログは動画の準備と転送時間を分けて記録し、要求された並列度と実際の並列度、
接続数、再試行回数を報告します。トレースログにはチャンクごとの試行、確認応答の
進捗、失敗の状況が含まれます。並列度を高めても特定の速度が保証されるわけでは
ありません。性能を判断する前に、キャッシュされたアップロードを除外し、同じファイルと
同じネットワーク条件で比較してください。

回帰テストは分離されたトランスポートを使用し、並列度の上限、順序が入れ替わった
確認応答、途中で停止した先行チャンク、再試行の枯渇、バックプレッシャー、クリーンアップを
対象とします。これらのテストは、実際の QQ への配信やアップロードのスループットを
証明するものではありません。

## アップロードのタイムアウトとノード選択

すべての Highway HTTP アップロード（画像、ボイス、動画、ファイルを含む）は、
各ファイルの転送開始時に次のデプロイ全体の環境変数をスナップショットします。

| 変数 | 既定値 | 意味 |
| --- | --- | --- |
| `SNOWLUMA_HIGHWAY_UPLOAD_IDLE_TIMEOUT_MS` | `30000` | 1 回のリクエスト中にレスポンスバイトが到着しない状態の最大待機時間（ミリ秒）。レスポンスバイトが到着するとリセットされます。 |
| `SNOWLUMA_HIGHWAY_UPLOAD_TIMEOUT_MS` | `1800000` | 1 ファイルの転送予算の合計（ミリ秒、30 分）。すべてのチャンク、接続、書き込み、レスポンス待機、再試行遅延で共有されます。 |

たとえば、小さな画像を送信するデプロイでは次のように指定できます。

```sh
SNOWLUMA_HIGHWAY_UPLOAD_IDLE_TIMEOUT_MS=5000
SNOWLUMA_HIGHWAY_UPLOAD_TIMEOUT_MS=120000
```

これらの変数を付けてプロセス／コンテナを再起動してください。どちらの値も
1 から 2147483647 までの整数である必要があります。不正な値は、既定値を暗黙に
使用するのではなく、アップロードを可視的に失敗させます。予算の合計は、チャンクの
成功後、受信バイトの到着後、別のノードへの切り替え時にもリセットされません。
アイドルタイマーは HTTP リクエストの開始時（書き込みを含む）に起動するため、
低速な接続ではより大きな値が必要になる場合があります。ソースのダウンロード、
ハッシュ計算、QQ アップロードの準備は、この転送予算より前に実行されます。
動画本体とそのカバーは別々のファイルであり、別々の予算を持ちます。

トランスポート障害では、未確認のチャンクのみを再試行します。各チャンクには
少なくとも 3 回の試行、または指定された候補が 3 つより多い場合はすべての異なる
候補を網羅するのに十分な回数の試行が、ファイルの予算の合計を条件として許可されます。
各接続には 3 秒のハンドシェイク制限があります。予算の合計が期限切れになると、
すべてのワーカーが中断され、その接続が閉じられます。未完了のファイルシステム
読み取りはソースを閉じる前にドレインされるため、クリーンアップはその期限の後に
完了できます。サーバーによる明示的な拒否と不正な確認応答は、引き続き即座に
失敗します。バックプレッシャーによる再試行は別途上限が設けられ、同じファイルの
期限を共有します。

ノードの観測結果はアカウントセッションとアップロード種別に属し、完全なホストと
ポートをキーとします。検証済みの成功したアップロード確認応答は 5 分間優先されます。
トランスポート障害は、そのエンドポイントの優先度を 30 秒間下げます。未知の
エンドポイントは直近の失敗より優先して候補に残り、失敗によって候補が恒久的に
除外されることはありません。選択できるのは現在のアップロードに対して指定された
宛先のみです。履歴はアカウントセッションごとに最大 128 件の観測結果を保持し、
チケットやペイロードを含まず、そのアカウントの識別情報オブジェクトが破棄されると
解放されます。プロセスを再起動すると履歴は消去されます。

TRACE ログには、実際に適用されるタイムアウトと候補の順序が表示されます。
読み取りタイムアウトには、現在の書き込み／読み取りフェーズ、完了した書き込み
バイト数、受信バイト数、レスポンスヘッダーを確認したかどうかが含まれます。
予算の合計の枯渇は別途 `upload_timeout` として報告されます。失敗した転送は
失敗した OneBot アクションのままです。

## メディアダウンロードの制限

2 つのデプロイ全体の設定値が、`highway/utils.ts` における HTTP メディア
ダウンロードを制限します。これらはアカウント単位の OneBot 設定ではなく環境変数です。
すべての呼び出し元が同じダウンロードエンジン（`loadBinarySource` /
`stageSourceToDisk`）に到達するためです。

```sh
SNOWLUMA_HTTP_DOWNLOAD_TIMEOUT_MS=180000
SNOWLUMA_MAX_BINARY_DOWNLOAD_BYTES=2147483648
```

どちらも以前のハードコードされた値が既定値であるため、未設定のデプロイは
以前とまったく同じように動作します。不正な値はログに記録されて無視され、
既定値にフォールバックします。すでに明示的な上限を渡している呼び出し元は
それを維持します。グループ／プライベートファイルとフラッシュ転送は引き続き
4 GiB を使用し、インラインの `base64://` / `data:` フラッシュソースは
1 GiB のバッファリング読み込み上限を維持します。

`SNOWLUMA_HTTP_DOWNLOAD_TIMEOUT_MS` は
`SNOWLUMA_DOWNLOAD_FILE_TIMEOUT_MS`（`download_file` OneBot アクションで使用）
とは関係ありません。前者は highway のメディアダウンロードを制限し、後者は
そのアクション自身のファイルステージングを制限します。
