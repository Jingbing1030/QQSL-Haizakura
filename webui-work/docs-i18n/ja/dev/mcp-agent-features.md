# MCP エージェント機能


これらの追加は、既存のツール名、アクションパラメーター、テキスト結果、読み取り / 書き込みゲートを維持します。カタログツールやローカルランタイムの概要からエンドポイントへ接続することはありません。アクションカタログは同梱されたスナップショットのままであり、接続先サーバーの能力についての主張ではありません。

## プロトコル互換性とカタログのキャッシュ

同じ `snowluma-mcp` の stdio コマンドが、MCP `2026-07-28` のクライアントと、`initialize` ハンドシェイクを使う古いクライアントの両方を受け付けます。公式のサーバー SDK が接続ごとにプロトコルを選択します。モダンなクライアントは初期化なしで `server/discover` とリクエスト単位のメタデータを利用できます。レガシークライアントは既存の設定のまま動作します。これにより公開で待ち受ける MCP HTTP エンドポイントが増えることはありません。

モダンな応答には、プロトコルの完了情報とサーバーメタデータが含まれます。キャッシュのヒントは、応答が静的なカタログデータを含むか、非公開のライブ状態を含むかによって変わります：

| 応答 | 有効期間 | スコープ |
| ----------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------ |
| `tools/list` | 5 分 | `private`。モードとクライアントの能力がツールのメタデータと可用性に影響します。 |
| `resources/list` | 5 分、イベントが有効なときは 0 | `private`。UI の能力と有効なイベントリソースが一覧に影響します。 |
| `resources/templates/list` | 5 分 | `public`。同梱のテンプレート一覧は静的です。 |
| アクションカタログまたはメッセージ UI に対する `resources/read` | 5 分 | `public`。これらは同梱の静的アセットです。 |
| イベントリソースに対する `resources/read` | 0 | `private`。アカウントのイベントと接続状態を含みます。 |

これらはクライアント側のキャッシュヒントであり、サーバー側の結果キャッシュではありません。ランタイム概要を含むツール呼び出しには、これらのヒントが付くことはありません。SDK はレガシークライアント向けにモダン専用の結果フィールドを省略します。未対応のプロトコルリビジョンはアクション実行前に拒否され、アクションのリトライを引き起こすことはありません。

## 呼び出しのトレース

すべてのツール呼び出しには W3C のトレースコンテキストが付きます。クライアントはツールリクエストの `_meta` に `traceparent` と任意の `tracestate` を指定できます：

```json
{
  "name": "query_action",
  "arguments": { "action": "get_status" },
  "_meta": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
  }
}
```

MCP は有効な呼び出し側のトレース ID を保持し、呼び出しごとに新しいスパン ID を生成します。有効な親がない場合は独立したトレースを生成します。返される `_meta.traceparent` は、ツールのエラーを含めてその呼び出しを識別します。既存のテキストおよび構造化結果のエンベロープは変わりません。これは両方のプロトコル世代で動作します。

通常のリクエスト、ストリーム、自動アップロードのチャンク、アップロードのクリーンアップは、呼び出しコンテキストを HTTP ヘッダーで転送し、OneBot のアクションパラメーターでは決して転送しません。並行する呼び出しは独立したヘッダーを保ちます。呼び出しを追跡するには、MCP の stderr 診断にあるその traceparent を Haizakura の `http_trace` エントリと照合し、そのエントリの既存の `req#` をアクションのライフサイクルログに沿って追ってください。Haizakura 側の相関には TRACE ログと有効な認証済み HTTP リクエストが必要で、リモートのトレース ID がそのローカルなリクエスト ID を置き換えることはありません。テレメトリーのエクスポーターは導入されていません。

MCP の呼び出し診断に含まれるのは、既知のツール名、traceparent、結果、失敗カテゴリ、所要時間であり、メッセージの内容、トークン、ファイルパス、任意のメタデータは含まれません。`tracestate` は最大 512 文字・32 メンバーで検証され、転送はされますがログには記録されません。不正なトレースメタデータは固定の診断を生成し、それ以外が有効なアクションを拒否することはありません。`baggage` は転送もログ記録もされません。トレース識別子は相関のためのデータであり、認証や権限ではありません。

## 任意の実行サービス

既存の設定はそのまま動作します。入力の補完とメッセージのプレビューは追加のツールであり、イベント接続と永続タスクは明示的な設定を必要とします。たとえば、MCP クライアントのサーバー環境で次の変数を設定し、アドレス、認証情報、パスを意図する Haizakura インスタンスのものに置き換えてください：

```json
{
  "SNOWLUMA_MCP_MODE": "write",
  "SNOWLUMA_MCP_ENDPOINT": "http://127.0.0.1:3000/",
  "SNOWLUMA_MCP_TOKEN": "<your access token>",
  "SNOWLUMA_MCP_EVENTS_URL": "ws://127.0.0.1:3001/event",
  "SNOWLUMA_MCP_TASK_DIR": "/absolute/private/mcp-tasks",
  "SNOWLUMA_MCP_UPLOAD_ROOT": "/absolute/allowed/uploads"
}
```

HTTP と WebSocket のアドレスはそれぞれ独立に設定するサーバーエンドポイントであり、WebSocket のアドレスが HTTP のアドレスから推測されることはありません。イベントは `SNOWLUMA_MCP_TOKEN` を認証ヘッダーで再利用します。アップロードとタスクのディレクトリは MCP ホスト上にあります。不要なサービスは省略してください。docs モードはオフラインのままです。

## 不足パラメーターの補完

`query_action_with_input` と `invoke_action_with_input` は、`query_action` と `invoke_action` と同じ引数、アクションの検索、モードゲートを使用します。既存のツールはこれまでとまったく同じように動作し続けます。追加のツールは、アクションカタログのトップレベルの `required` 配列に記載されたフィールドが存在しない場合にのみ入力を求め、条件付きの要件や任意の値を推論することはありません。

たとえば、`{"action":"send_group_msg","params":{"group_id":20001}}` を渡した `invoke_action_with_input` は、不足しているメッセージを求めます。フォームには 1 つの `params_json` 文字列があり、その中身は `{"message":"Hello"}` のような JSON オブジェクトです。回答は、通常のアクション実行の前に、不足フィールドのカタログスキーマに対して検証されます。すでに指定されたフィールド、アクション名、実行オプションは上書きできません。余分な回答フィールドは拒否されます。辞退、キャンセル、または不正な回答はアクションを実行しません。

クライアントはフォームによる elicit のサポートを宣言する必要があります。モダンなクライアントは `resultType: "input_required"` を受け取り、SDK のリクエスト状態と入力応答の仕組みを使って再開します。elicit をサポートするレガシークライアントは SDK の `elicitation/create` フローを使用します。フォームをサポートしないクライアントはツールエラーを受け取り、代わりに元のツールへ完全な引数を渡すことができます。

継続状態は署名され、元のツールと引数に結び付き、10 分で失効し、実行前に 1 回だけ消費されます。並行または繰り返しの回答が同じ継続を 2 回実行することはできません。1 つのランタイムが保持する保留中のプロンプトは最大 256 個で、再起動すると作業を再生するのではなくそれらを無効化します。引数がそろっている場合は入力のやり取りを完全に迂回します。この機能は汎用的な承認ゲートではなく、既存のアクション呼び出しに確認プロンプトを追加するものでもありません。

## ライブイベントリソース

`SNOWLUMA_MCP_EVENTS_URL` を設定すると、読み取りモードと書き込みモードが `subscribe_events` と `unsubscribe_events` を公開します。URL は `ws:` または `wss:` を使い、認証情報、クエリパラメーター、フラグメントを含んではいけません。ツールやリソースを一覧しても接続は行われず、イベント接続を開くのは `subscribe_events` だけです。

```json
{
  "self_id": 10001,
  "types": ["message", "notice"],
  "group_ids": [20001],
  "user_ids": [30001]
}
```

必須の `self_id` には、ログイン済みであることが期待されるアカウントを指定してください。必要であれば `get_login_info` で取得できます。受信するすべてのイベントはこのアカウントに一致しなければなりません。アカウントの不一致や不正なイベントは接続を停止させ、表面化します。任意の型は `message`、`notice`、`request` で、型を省略すると 3 つすべてを意味します。`message_sent` は message カテゴリに含まれます。グループとユーザーのフィルターは AND で結合されるため、グループフィルターを指定すると一致する `group_id` を持たないイベントは除外されます。各 ID フィルターは最大 100 個の異なる正の整数を受け付けます。

結果には正規の `snowluma://onebot/events/<id>` リソース URI が含まれます。`resources/read` で読み取り、以降の読み取りでは `?after=<next_cursor>` を使ってより新しいバッファー内のエントリを取得します。カーソルはその 1 つのリソースに属します。応答には `status`、`next_cursor`、`oldest_cursor`、`dropped_events`、`gap`、`notification_failed` が含まれます。読み取りはイベントを消費しません。利用できるのはサブスクリプション作成後に受信したイベントだけで、これはメッセージ履歴のストレージではありません。

各リソースは最大 256 個のイベントと 1 MiB のイベントデータを保持します。1 つのランタイムは最大 16 個のリソースをサポートし、1 つのアカウント接続を共有します。受信フレームは 256 KiB に制限されます。バッファーの追い出しと切断は、カーソル / gap と status のフィールドを通じて引き続き可視であり、サービスが暗黙に再接続したり、欠落したイベントが回復されたと主張したりすることはありません。アカウントを変更する前、または切断後に新しい接続を作成する前に、既存のリソースを解放してください。

更新を受け取るには、**`?after` を付けない正規の URI** を使用します：

- モダンなクライアントは `resourceSubscriptions: [uri]` を指定して `subscriptions/listen` を使用します（TypeScript SDK は `client.listen(...)` を公開しています）。その通知ストリームを閉じてもイベントバッファーは解放されません。明示的に `unsubscribe_events` を呼び出してください。
- レガシークライアントはまず正規の URI で `resources/subscribe` を呼び出し、その後 `notifications/resources/updated` を受け取ります。`resources/unsubscribe` もそのイベントリソースを解放します。明示的な unsubscribe ツールは両方の世代で動作します。

更新通知はリソースが変化したことを示すだけです。データを読むにはリソースを取得してください。最後のリソースを解放すると WebSocket が閉じられます。MCP 接続を閉じると、そのイベントリソースとバッファーが解放されます。イベント操作が OneBot のビジネスアクションを実行したり、QQ メッセージを送信したりすることはありません。

## 永続的なバックグラウンド転送

絶対パスの `SNOWLUMA_MCP_TASK_DIR` を設定し、書き込みモードを使うと永続タスクが有効になります。タスクツールはさらに、`extensions: {"io.modelcontextprotocol/tasks": {}}` を宣言する MCP `2026-07-28` のクライアントを必要とします。レガシークライアントは既存の同期実行ツールを使い続けます。このサーバーは廃止された `tasks/list` や `tasks/result` のプロトコルメソッドを公開しません。

`invoke_action_background` は `invoke_action` と同じ引数を取りますが、ストリームとしてマークされたカタログのアクションのみを受け付けます。たとえば、設定されたアップロードルート内の `execution.input_file` を指定して `upload_file_stream` を実行できます。作業を開始する前にタスクレコードを書き込み、`resultType: "task"` のハンドルを返します。通常のアクションは既存のツールを通じて引き続き実行されます。現在のバックグラウンド転送のエントリは `_with_input` と自動的に組み合わされることはありません。開始する前に必要な転送パラメーターを指定してください。

- `{ "taskId": "..." }` を渡した `tasks/get` は現在の状態を返し、完了していれば保存された結果またはエラーを返します。`completed` のタスクが失敗したビジネス応答を含むことがあります。ネストした結果の diagnostics、`status`、`retcode` を確認してください。
- `tasks/cancel` は協調的なキャンセルを要求します。キャンセルはリモートの効果を取り消しませんし、すでに進行中の正常な完了が競争に勝つこともあります。最終状態を得るためにタスクを再度ポーリングしてください。
- `tasks/update` は、未処理のタスク入力リクエストに対する入力応答のみを受け付けます。これはプロトコルのライフサイクルエンドポイントであり、任意のタスク編集 API ではありません。現在のバックグラウンド転送のエントリ自体は対話的な入力を要求しません。
- `list_tasks` は結果本体を含まないタスクのメタデータを返す MCP ツールです。任意の `cursor` と `limit`（1〜100、既定 50）を受け付け、次のページがある場合は `nextCursor` を返します。

タスクのハンドルは `pollIntervalMs: 1000` と `ttlMs: null` を通知します。結果は再起動をまたいで残り、自動的に失効したり削除されたりすることはありません。再起動は未完了の作業を、明示的な **リモート結果不明** というメッセージを伴って失敗としてマークし、その操作を再生することは決してありません。これが永続化するのは転送の状態 / 結果であり、再開可能なアップロードやダウンロードの実行ではありません。同時実行できるタスクは最大 4 つで、永続化される各タスクレコードの上限は 16 MiB です。

ストレージは排他的なランタイムリース、非公開のディレクトリ / ファイル（POSIX では 0700/0600）、検証済みのレコードを使用します。破損、権限エラー、書き込みの失敗はエラーとして残ります。ディレクトリは有効なモード、エンドポイント、トークンのダイジェストに結び付けられ、その設定を変更するとディレクトリの再利用が拒否されます。新しい設定には新しい非公開ディレクトリを選び、古い履歴は保持してください。認証情報はスコープレコードに保存されませんが、タスクの結果には非公開のアカウントデータが含まれ得るため、それに応じて保護してください。

## メッセージプレビューパネル

`preview_message` はすべてのモードで利用でき、ドラフトを構築するだけです：

```json
{
  "message_type": "group",
  "target_id": 20001,
  "text": "Hello",
  "reply_to": -123456
}
```

プライベートな会話には `private` を使用します。`target_id` は正の安全な整数である必要があり、任意の `reply_to` は非ゼロの符号付き 32 ビットメッセージ ID です。プレビューがサポートするのはリテラルテキストと任意の引用返信であり、メディアのレンダリングは行いません。メッセージの制御コードに似たテキストは、リテラルテキストのまま扱われます。

すべてのクライアントが同じ可読テキストのドラフト、`can_send` フラグ、対応する `invoke_action` の引数を受け取ります。MCP Apps 拡張 `io.modelcontextprotocol/ui` を MIME タイプ `text/html;profile=mcp-app` で宣言したクライアントだけが、そのツールの UI メタデータと列挙された UI リソースを受け取ります。パネルは公式の Apps クライアントでビルドされた、同梱の自己完結型 HTML アセットです。外部のスクリプト、フォント、メディアを読み込まず、自前のネットワーク接続を開かず、外部のテキストを HTML として解釈せずに表示します。パッケージ済みのアセットが欠けている場合は、可視のパッケージングエラーとなります。

パネルを読み込んでも何も送信されません。その送信ボタンは、ユーザーがクリックした後にのみ、ホスト経由で既存の `invoke_action` を呼び出し、サーバーの書き込みゲートは引き続き適用されます。読み取り / docs モードや、サーバーツールをサポートしないホストでは、送信は無効のままです。パネルは二重クリックを防ぎ、失敗または結果不明の送信をリトライしません。結果を確認してから新しいドラフトを作成してください。正常な応答は、QQ での配信やレンダリングの証明ではありません。

## アクション結果のスキーマと例

`get_action` と `snowluma://onebot/actions` は、別名を含む同梱のすべてのアクションについて `returnsSchema` と `examples` を含みます。どちらも OneBot のアクション定義のそばで記述され、生成されたカタログへコピーされます。一覧 / 検索の応答は簡潔なままで、完全なコントラクトを取得するには `get_action` を使用してください。

`returnsSchema` は成功した OneBot の **`data`** を記述するものであり、OneBot のエンベロープ全体や MCP の `structuredContent` ラッパーではありません。読む前に `status` と `retcode` を確認してください。ストリームアクションでは、スキーマは成功した各フレームの `data` を記述します。一方、MCP のダウンロードは保存済みファイルのメタデータを返し、汎用ストリームはフレームのコレクションを返します。エラーフレームと失敗したエンベロープは成功結果ではありません。未対応のアクションは成功結果を持たないため `{ "not": {} }` を使用します。互換性のためのプレースホルダーは、その制限を明示的に記述しています。

各 example には `summary`、`params`、および前提条件と識別子の出所を説明する任意の `notes` があります。これらは例示的な呼び出しであり、カタログツールが実行することは決してありません。実行前に、example のアカウント / グループ ID、不透明なハンドル、パスを現在のアカウントの値に置き換えてください。notes は、すべてのチャンクが確認された後にアップロードを完了するなど、複数ステップを要する操作を識別します。

たとえば `get_action({ "name": "get_msg" })` は符号付きメッセージ ID を記述します：

```json
{
  "action": "get_msg",
  "params": { "message_id": -123456 }
}
```

このオブジェクトを実際のメッセージ ID とともに `query_action` へ渡してください。書き込みとストリームは書き込みモードで `invoke_action` を使用します。自動アップロードでは、設定されたアップロードルート内の実在するファイルを指定して
`{ "action": "upload_file_stream", "execution": { "input_file": "/allowed/hello.txt" } }` を `invoke_action` へ渡します。通常のアクションのパスは Haizakura サーバーを指すのに対し、`execution.input_file` と MCP のダウンロードパスは MCP ホストを指します。

符号付きメッセージ ID の代わりにゼロを代入しないでください。リソースのみの転送アップロードとフラッシュ共有には、ドキュメント化された `message_id: 0` というセンチネルがあり、メッセージの検索や撤回には使用できません。また、`null` と `{}` の違い、任意フィールド、メディアの `file_size` のような 10 進文字列は、ドキュメントどおりに正確に保ってください。

## 構造化結果

完了したツールの結果は、通知された `outputSchema` を使用し、既存の `content` テキストブロックと並べて `structuredContent` を返します。モダンな `input_required` とバックグラウンドタスクのハンドルはプロトコルの継続であり、まず `resultType` を確認し、完了した結果は該当する継続またはタスクのライフサイクルを通じて取得してください：

```json
{
  "result": { "status": "ok", "retcode": 0, "data": { "message_id": -123 } },
  "diagnostics": { "outcome": "success" }
}
```

`result` は元のペイロードで、カテゴリ一覧のような配列も含みます。MCP のツールエラーのときは `null` です。`diagnostics.outcome` は `success`、`failed`、`unknown` のいずれかで、失敗には `kind`、`message`、`next_step` が含まれることがあります。

通常の OneBot のビジネス上の失敗は、`isError` を設定せずに元のエンベロープを返します。失敗は構造化された diagnostics で示されます。非同期の応答や、成功を確認しない応答の outcome は `unknown` です。転送エラーと既存のツール / ストリームエラーは引き続き `isError: true` を設定します。エラーカテゴリは既知の原因を記述するもので、分類されていない実行エラーがメッセージ文字列から推測されることはありません。ツールの実行も接続チェックも自動的にリトライしません。負のメッセージ ID は有効なままで、変更されずに保持されます。

## 検索、フィルター、ページネーション

`search_actions` は、`match: "keywords"` が要求されない限り、元の大文字小文字を区別しない部分文字列一致とカタログ順を保ちます。キーワードモードはスペース区切りの語を AND で結合し、少数の一般的な中国語 / 英語の同義語を認識し、完全一致するアクション名や別名を先頭にランク付けします。

```json
{
  "query": "群 禁言",
  "match": "keywords",
  "read_only": false,
  "stream": false,
  "limit": 10,
  "offset": 0
}
```

`list_actions` と `search_actions` はどちらも任意の `category`、`read_only`、`stream`、`limit`（1〜200）、`offset`（非負の整数）を受け付けます。ページネーションを省略すると一致する完全な一覧を返し、`{count, actions}` を保ちます。`limit` または `offset` を指定した場合、`count` は返されたページのサイズ、`total` は一致する総数、`next_offset` は次のページのオフセットまたは `null` です。ページネーションは同梱のカタログに適用され、サーバーへのリクエストを発行することはありません。

## ランタイム概要

`get_runtime_info({})` は次を返します：

- 有効な `mode`、`execution_enabled`、`write_enabled`。
- 同梱カタログのバージョンとアクション数。`server_support` は `unknown` のままで、バージョンが一致するだけではアクションのサポートを証明しません。
- 実行モードでは、有効なリクエストタイムアウト、ファイルサイズとディレクトリクォータの上限、同時ストリームの上限、ダウンロードディレクトリ、アップロードルート、自動アップロードが有効かどうか。docs モードでは `transport` は `null` です。
- `connection_checked: false`。ローカルの設定は、ログインが生きていることの証明ではありません。

概要はエンドポイント、アクセストークン、認証ヘッダーを公開しません。設定されたファイルパスは MCP ホスト上のパスです。すべてのストリームアクションは引き続き書き込みモードを必要とし、`upload_enabled` は設定されたファイルルートを記述するものであって、そのゲートを迂回する権限ではありません。

`get_runtime_info({"check_connection": true})` は、クライアントを伴う読み取り / 書き込みモードでのみ利用できます。通常の読み取り専用の実行ゲートを使って `get_login_info`、`get_status`、`get_version_info` を明示的に照会します。`checks` の各エントリには、元の応答と diagnostics が含まれます。部分的な失敗は可視のままです。オンライン状態は返された status データで確認してください。HTTP のやり取りが成功しただけでは、アカウントがオンラインであることを確立できません。

## キャンセルと進捗

MCP のキャンセルは、レスポンスボディの読み取りを含め、ストリームアクションだけでなく通常の HTTP 呼び出しにも届くようになりました。通常の呼び出しはリクエストタイムアウトを保ち、ストリームは接続と読み取りごとのアイドルタイムアウトを別々に保ちます。キャンセルされた呼び出しは自動的にリトライしません。キャンセルやタイムアウトはリモートの書き込みの結果を不明のままにすることがあります。待機を止めても、Haizakura がすでに受信した操作が取り消されるわけではありません。

呼び出し側が `_meta.progressToken` を含めると、ストリーム実行は同じトークンで標準の `notifications/progress` 通知を発行します。ファイルのダウンロードはデコードされて書き込まれたバイト数を報告し、自動アップロードはサーバーが確認したバイト数を報告します。汎用ストリームは受け入れられたフレーム数を報告します。合計は、正のファイルサイズが判明している場合にのみ含まれます。空のファイルとサイズ不明のダウンロードでは省略されます。

通知は 250 ms あたり 1 回に制限され、加えて成功応答の前に最後の保留中の更新が送られます。値は増加し、通知はキャンセルまたは完了で停止し、進捗トークンを持たない呼び出し側は何も受け取りません。通知の配信失敗は表面化します。進捗は転送されたデータを記述するもので、最終的なコミットではありません。ファイルの検証と完了を確認できるのは、成功したツール結果だけです。

既存のファイルの封じ込め、クォータ、部分ファイルのクリーンアップ、アップロードリセットの挙動は変わりません。ファイルのバイト列が進捗メッセージに現れることはありません。
