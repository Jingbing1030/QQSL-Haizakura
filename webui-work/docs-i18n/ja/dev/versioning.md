# @snowluma/sdk のバージョニング


SDK は公開パッケージの範囲について SemVer に従います。

- `@snowluma/sdk` からエクスポートされる実行時の値とクラス。
- `@snowluma/sdk` および `@snowluma/sdk/types` からエクスポートされる型。
- サポート対象のサブパスエクスポート: `client`、`messages`、`events`、`errors`、`actions`、`types`、`node`。
- 型付きクライアントヘルパー、メッセージビルダー、イベントヘルパー、SDK のエラークラスの実行時の挙動。

## バージョンポリシー

SDK のバージョンとアプリケーションのバージョンは、リポジトリのルートで `pnpm bump <version>` を実行して同期します。

現在の Node.js の要件は `^24.22.1 || >=26.12.1` です。開発とビルドにはリポジトリの `.node-version` を使用してください。

SDK は ES モジュールパッケージであり、Node.js のネイティブインポートとバンドラー経由の利用の両方をサポートします。ビルドには `NodeNext` を使用しており、ソース内の相対インポートと再エクスポートには `.js` 指定子が必要です。これにより、出力される JavaScript と宣言ファイルの双方がバンドラーなしで解決できます。パッケージのテストでは、新しく生成した出力をコンパイルし、すべての実行時エントリポイントを Node.js で読み込み、利用側の型を NodeNext とバンドラー解決の両方で型チェックします。

- メジャー: 公開エクスポートの削除または変更、実行時の挙動の非互換な変更、サポート対象の Node バージョンの変更、既存のパッケージサブパスの削除または変更。
- マイナー: 新しい公開 API やパッケージサブパスの追加、新しい Haizakura アクションのサポート、省略可能なパラメータの追加、エラーサブクラスの追加。
- パッチ: バグの修正、ドキュメントの改善、公開型を壊さない範囲での実装詳細の限定、呼び出しシグネチャを変えないアクションメタデータの更新。

## リリースチェックリスト

1. `pnpm bump <version>` を実行し、すべてのワークスペースのバージョンを更新します。
2. `packages/sdk/CHANGELOG.md` を更新します。
3. `pnpm --filter @snowluma/sdk typecheck` を実行します。
4. `pnpm --filter @snowluma/sdk test` を実行します。
5. `pnpm --filter @snowluma/sdk build` を実行します。
6. `pnpm --filter @snowluma/sdk pack --dry-run` を実行し、公開されるファイルを確認します。

## npm への自動公開

`.github/workflows/sdk-npm-publish.yml` は、SDK 関連のファイルが `main` に到達したときに `@snowluma/sdk` を公開します。これには `dev` から `main` への自動昇格フローも含まれます。公開ジョブは npm の Trusted Publishing を `Haizakura` という名前の GitHub Environment とともに使用します。GitHub Actions の OIDC で認証するため、`NPM_TOKEN` シークレットは必要ありません。

SDK、UI、MCP に対する npm の初回設定は
[`.github/npm-trusted-publishing.md`](../../.github/npm-trusted-publishing.md) に記載されています。

パッケージのバージョンが npm 上にすでに存在する場合、ワークフローはその回の公開をスキップします。新しい npm リリースを作成すべき SDK の変更をマージする前に、`packages/sdk/package.json` のバージョンを上げてください。

## アクションの互換性

`SNOWLUMA_ACTIONS`、`isHaizakuraAction`、`HaizakuraKnownAction` は `@snowluma/sdk` と `@snowluma/sdk/actions` の両方から利用できます。カタログには、今回のリリースで実行可能なアクション名、互換性のためのエイリアス、生のアクションが含まれます。OneBot 側のレジストリテストは、SDK のカタログがサーバーと整合し続けることを検証します。公開される SDK がサーバーのコードをインポートすることはありません。

このローカルカタログは、接続中のサーバーに対する機能の有無を確認するものではありません。既知のすべてのアクション名には、エイリアスを含めて `HaizakuraActionMap` に対応するパラメータと結果のエントリがあります。既存の広範な JSON 契約は互換性のために維持されます。新しいパラメータ型は、数値文字列やプリミティブの型変換を含む、受け付ける入力形式を記述します。サーバー側の範囲と状態の検証は引き続き適用されます。カスタムアクションと動的に選択される名前は、`raw()` と `rawResponse()` を通じて引き続きサポートされます。アクション型の追加は、既存のメソッドシグネチャや戻り値の型を変更しない限りマイナーな変更です。

ストリームの結果型は、中間フレームと終端フレームを含む個々のフレームのペイロードを記述します。組み込みの両クライアントは `requestStream()`（エンベロープ）と `stream()`（API エラー処理を伴うペイロード）に加えて、差分アップロード / ダウンロード用のヘルパーをサポートします。詳しくは [STREAMING.md](STREAMING.md) を参照してください。既存の `request()`、`call()`、`raw()`、`rawResponse()`、`downloadFile()` は単一応答の契約を維持します。`request()` だけを実装したカスタムサブクラスは引き続き有効です。既定の `requestStream()` はストリーミングが未サポートであることを明示的に報告します。ストリームのリセット / エラーエンベロープは既存のエラー挙動を維持します。10 進文字列として返されるアルバムの件数と ID は文字列のままであり、通常のメッセージ ID は符号付き数値のままです。

パッケージの利用側テストは、アクションマップの完全な網羅、推論される結果、互換性のためのエイリアス、無効な入力の例を、NodeNext とバンドラー解決の両方で検証します。同じパラメータの例は、QQ を起動せずアクションも実行せずに、サーバーの実際のアクションパーサーに対して検証されます。

追加的なメディア送信メソッド、明示的な引用返信、WebSocket イベントの待機については [MESSAGING.md](MESSAGING.md) に記載されています。既存の文字列パス、通常の `reply()` の挙動、ハンドラー / コンテキストの型は引き続きサポートされます。省略可能な `node` サブパスがローカルファイルシステムへのアクセスを担い、ブラウザ向けのエントリポイントは Node のインポートを含みません。また実行時は、グループファイルのチャット公開に失敗した場合に成功を返さず、その失敗を伝播します。成功したアクションの応答形状は変わりません。

省略可能な `node` エントリは、`createReverseWebSocketServer`、`HaizakuraReverseWebSocketServer`、リバースセッションの型もエクスポートします。これらの追加的なエクスポートは、フォワードクライアントを変更せずに OneBot のリバース接続を受け付けます。`ws` の実行時依存は Node エントリだけが読み込み、ブラウザ向けのエクスポートは Node のサーバーインポートを含みません。詳しくは [REVERSE_WEBSOCKET.md](REVERSE_WEBSOCKET.md) を参照してください。
