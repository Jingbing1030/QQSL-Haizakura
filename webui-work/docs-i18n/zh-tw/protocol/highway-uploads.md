# 媒體傳輸設定


## 影片上傳連線

影片上傳預設使用一條連線。在 **設定 → 全域設定 → 影片上傳連線** 中，可選擇 1、2、3 或 4 條連線。`config/snowluma.json` 中的等效設定為：

```json
{
  "videoUploadConcurrency": 1
}
```

此設定套用於所有帳號。透過 WebUI 儲存會影響下一次影片上傳；已在準備或傳送中的上傳會保留其原始值。手動編輯檔案後請重新啟動 Haizakura。較舊設定中缺少此值代表一條連線。無效的值會被回報，不會被截斷至範圍內。部分設定儲存與設定備份都會保留此設定。

平行處理只套用於影片主體。封面、圖片、語音訊息與檔案上傳維持其既有行為。不大於 2 MiB 的影片仍使用一條連線。最後一個影片區塊會等到前面所有區塊都被確認後才送出。此設定不會改變 OneBot 動作、訊息區段或回應結構。

連線中斷時只會重試其未確認的區塊，且在有限的重新嘗試預算內。已知的伺服器背壓會把該次上傳降為一個作用中的請求，並在延遲後重試。伺服器拒絕、無效的確認或重新嘗試預算耗盡都會使上傳失敗。失敗的上傳絕不會被默默回報為已送出。

除錯日誌會把影片準備與傳輸時間分開，並回報要求的與實際生效的並行度、連線數與重試次數。追蹤日誌包含每個區塊的嘗試、確認進度與失敗情境。較高的並行度不保證特定速度；在得出效能結論之前，請以同一個檔案與相同網路條件進行比較，並排除快取的上傳。

回歸測試使用隔離的傳輸，涵蓋並行度界限、亂序確認、早期區塊停滯、重試耗盡、背壓與清理。它們不構成真實 QQ 遞送或上傳輸送量的證明。

## 上傳逾時與節點選擇

所有 Highway HTTP 上傳（包括圖片、語音、影片與檔案）會在每個檔案開始傳輸時，快照這些部署範圍的環境變數：

| 變數 | 預設值 | 意義 |
| --- | --- | --- |
| `SNOWLUMA_HIGHWAY_UPLOAD_IDLE_TIMEOUT_MS` | `30000` | 單一請求期間在沒有回應位元組的情況下等待的上限，單位為毫秒。回應位元組到達時會重設。 |
| `SNOWLUMA_HIGHWAY_UPLOAD_TIMEOUT_MS` | `1800000` | 單一檔案的總傳輸預算，單位為毫秒（30 分鐘）。由所有區塊、連線、寫入、等待回應與重試延遲共用。 |

例如，傳送小型圖片的部署可以使用：

```sh
SNOWLUMA_HIGHWAY_UPLOAD_IDLE_TIMEOUT_MS=5000
SNOWLUMA_HIGHWAY_UPLOAD_TIMEOUT_MS=120000
```

請帶著這些變數重新啟動行程/容器。兩個值都必須是 1 到 2147483647 之間的整數；無效的值會讓上傳明顯失敗，而不是默默使用預設值。總預算不會在區塊成功後、收到傳入位元組後，或換到不同節點時重設。閒置計時器會在 HTTP 請求開始時啟動，包括寫入階段；慢速連線可能需要更大的值。來源下載、雜湊計算與 QQ 上傳準備都在此傳輸預算之前進行。影片主體與其封面是各自獨立的檔案，擁有各自的預算。

傳輸失敗只會重試未確認的區塊。每個區塊至少允許三次嘗試；當提供的相異候選節點超過三個時，則允許足以涵蓋所有候選的嘗試次數，但仍受該檔案的總預算約束。每條連線有三秒的握手限制。總預算到期會中止所有工作人員並關閉其連線；關閉來源之前會先排空尚未完成的檔案系統讀取，因此清理可以在該期限之後完成。明確的伺服器拒絕與無效確認仍會立即失敗。背壓重試另有獨立的上限，並共用相同的檔案期限。

節點觀察結果屬於帳號會話與上傳類型，並以完整主機與連接埠為鍵。經驗證的成功上傳確認會在五分鐘內優先採用；傳輸失敗會把該端點的優先度降低三十秒。未知端點的可用性仍優先於最近的失敗，而失敗永遠不會永久排除某個候選。只有為目前這次上傳提供的目的地才能被選用。歷史記錄每個帳號會話最多保留 128 筆觀察結果，不含任何票證或承載資料，並會在該帳號的身分物件被丟棄時釋放。行程重新啟動會清除它。

TRACE 日誌會顯示實際生效的逾時與候選順序。讀取逾時包含目前的寫入/讀取階段、已完成的寫入位元組數、已接收的位元組數，以及是否已看到回應標頭。總預算耗盡會另外以 `upload_timeout` 回報；失敗的傳輸仍然是失敗的 OneBot 動作。

## 媒體下載限制

`highway/utils.ts` 中有兩個部署範圍的旋鈕可限制 HTTP 媒體下載。它們是環境變數而非個別帳號的 OneBot 設定，因為每個呼叫端都到達同一個下載引擎（`loadBinarySource` / `stageSourceToDisk`）：

```sh
SNOWLUMA_HTTP_DOWNLOAD_TIMEOUT_MS=180000
SNOWLUMA_MAX_BINARY_DOWNLOAD_BYTES=2147483648
```

兩者都預設為其先前的寫死值，因此未設定的部署行為與之前完全相同。無效的值會被記錄並忽略，退回預設值。已自行傳入明確上限的呼叫端會保留它：群組/私人檔案與閃傳仍使用 4 GiB，而內嵌的 `base64://` / `data:` 閃傳來源則保留 1 GiB 的緩衝載入上限。

`SNOWLUMA_HTTP_DOWNLOAD_TIMEOUT_MS` 與 `SNOWLUMA_DOWNLOAD_FILE_TIMEOUT_MS`（由 `download_file` OneBot 動作用使用）無關：前者限制 highway 媒體下載，後者限制該動作本身的檔案暫存。
