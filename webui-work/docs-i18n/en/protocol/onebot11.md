# OneBot v11 integration guide

> [!WARNING]
> This content was written entirely by AI; review it with care.

> This document describes Haizakura's (formerly SnowLuma's) implementation of the **OneBot v11** protocol:
> the 4 network access methods, authentication, message formats and event pushes.
>
> **Data sources**: `packages/onebot/src/config.ts` (configuration structure and validation),
> `packages/onebot/src/network/*.ts` (the adapter implementations) and
> `packages/onebot/src/event-filter.ts` (format branching),
> cross-checked against the live configuration from `GET /api/config/:uin` on a running instance.

---

## 1. Access methods at a glance

The implementation provides **4 adapter categories** (the `networks` structure in `config.ts`),
and the HTTP server can **additionally** enable WebSocket and SSE:

| Config key | Direction | Protocol | Who initiates | Typical use |
| --- | --- | --- | --- | --- |
| `httpServers` | Inbound | HTTP + optional WS + optional SSE | Framework/client → Haizakura | Most common; three protocols on one port |
| `httpClients` | Outbound | HTTP POST (reverse HTTP) | Haizakura → your HTTP service | Report events without a public IP |
| `wsServers` | Inbound | Forward WebSocket | Framework/client → Haizakura | Low-latency bidirectional |
| `wsClients` | Outbound | Reverse WebSocket | Haizakura → your WS service | **The first choice in the NapCat / go-cqhttp ecosystem** |

Additional switches (all belonging to the `httpServers` entry):

| Field | Default | Effect |
| --- | --- | --- |
| `enableWebSocket` | `false` | Additionally accept WebSocket upgrades on the same port |
| `enableSse` | `false` | Expose an SSE event stream at `GET <path>/_events` |

> **Deciding "forward" vs "reverse"**: it is based on **whether Haizakura is the server or the client**.
> `*Servers` = Haizakura listens (forward); `*Clients` = Haizakura dials out (reverse).

## 2. Configuration files and defaults

### 2.1 File locations

```
config/onebot.json            # 全局默认
config/onebot_<uin>.json      # 按账号覆盖（uin 纯数字）
```

- Read order: `config/onebot.json` → `config/onebot_<uin>.json`, the latter overriding the former.
- Only `onebot_<digits>.json` is recognized; **timestamp-style filenames** such as `onebot_1700000000.json`
  **are ignored** (source `PER_UIN_CONFIG = /^onebot_(\d+)\.json$/`).
- When the file is absent, the built-in defaults apply (see below).

### 2.2 Built-in default configuration

```json
{
  "networks": {
    "httpServers": [
      {
        "name": "http-default",
        "host": "127.0.0.1",
        "port": 3000,
        "path": "/",
        "enableWebSocket": false,
        "enableSse": false,
        "accessToken": "<随机 base64url>",
        "messageFormat": "array",
        "reportSelfMessage": false
      }
    ],
    "httpClients": [],
    "wsServers": [
      {
        "name": "ws-default",
        "host": "127.0.0.1",
        "port": 3001,
        "path": "/",
        "role": "Universal",
        "accessToken": "<随机 base64url>",
        "messageFormat": "array",
        "reportSelfMessage": false
      }
    ],
    "wsClients": []
  },
  "statusCommand": {
    "enabled": true,
    "swallow": false,
    "cooldownSeconds": 5,
    "trigger": "#Haizakura"
  },
  "historySync": { "enabled": false },
  "notifications": { "channelIds": [] }
}
```

> `accessToken` is generated by `randomBytes(32).toString("base64url")`, **43 characters**.
> It listens only on `127.0.0.1` by default; access from outside the container requires explicitly changing this to `0.0.0.0`.

### 2.3 Adapter fields

**Common fields** (all four categories)

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `name` | string | Auto-generated | Unique adapter name; a conflict refuses to load |
| `enabled` | bool | `true` | Set `false` to disable without deleting the configuration |
| `accessToken` | string | Random | Empty = **no authentication** |
| `messageFormat` | `"array"` \| `"string"` | `"array"` | Format of the message field |
| `reportSelfMessage` | bool | `false` | Whether to report messages you sent yourself |

Auto-naming prefixes: `httpServers` → `http-`, `httpClients` → `httppost-`,
`wsServers` → `ws-`, `wsClients` → `wsclient-`.

**`httpServers`** additionally:

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `host` | string | `0.0.0.0` | Listen address |
| `port` | int | — | **Required and > 0**, otherwise the entry is dropped |
| `path` | string | `/` | Base path |
| `enableWebSocket` | bool | `false` | Accept WS on the same port |
| `enableSse` | bool | `false` | Expose `_events` |
| `maxPayloadBytes` | int | See below | Inbound WS frame limit |

**`wsServers`** additionally: `host`, `port` (required, > 0), `path`,
`role` (`Api` / `Event` / `Universal`, defaulting to `Universal`) and `maxPayloadBytes`.

**`httpClients`** additionally: `url` (required, except with `enabled:false`) and `timeoutMs` (default `5000`).

**`wsClients`** additionally: `url` (required), `role` (default `Universal`),
`reconnectIntervalMs` (default `5000`, minimum `1000`) and `maxPayloadBytes`.

`maxPayloadBytes` ranges from **1024 to 2147483648** (2 GiB).
`httpClients` **does not accept** `maxPayloadBytes` (it reports a configuration error).

## 3. Authentication (accessToken)

### 3.1 Decision logic

Source `network/utils.ts`:

```js
function isAuthorized(request, token, allowRawToken = false) {
  if (!token) return true;                       // 未配置 token = 完全放行
  const auth = request.headers.authorization ?? "";
  if (auth === `Bearer ${token}` || (allowRawToken && auth === token)) return true;
  try {
    if (new URL(request.url ?? "/", "http://127.0.0.1")
          .searchParams.get("access_token") === token) return true;
  } catch {}
  return false;
}
```

### 3.2 Three ways to pass the token

| Method | Form | Applies to | Risk |
| --- | --- | --- | --- |
| Bearer header | `Authorization: Bearer <token>` | All adapters | ✅ Recommended |
| Raw token header | `Authorization: <token>` | **HTTP server only** | ⚠️ Non-standard, easily misread by middleware |
| URL query parameter | `?access_token=<token>` | All (WS handshake included) | 🔴 **The token enters the URL**: it lands in access logs, browser history, Referer headers and proxy logs |

> **Recommendation**: in production **use only the Bearer header**. `?access_token=` is kept only for compatibility with
> older clients; if you must use it in a browser, make sure full URLs are not logged.

### 3.3 Unauthorized response

```json
{ "status": "failed", "retcode": 1401, "data": null, "wording": "unauthorized" }
```

The HTTP status code is `401`. During the WS handshake the upgrade is rejected with `401 Unauthorized`
(the `verifyClient` callback, source `ws-server-adapter.ts`).

### 3.4 Authentication on reverse connections

| Adapter | Authentication header |
| --- | --- |
| `httpClients` | `X-Signature: sha1=<hex of HMAC-SHA1(accessToken, body)>` |
| `wsClients` | `Authorization: Bearer <accessToken>` |

`httpClients` **does not use** Bearer; it **signs the request body with HMAC-SHA1**
(source `computeHmacSha1`). Your receiving endpoint must verify with the same algorithm.

## 5. HTTP access in detail

### 5.1 Path → action name mapping

The configured `path` is the prefix, and **the remainder of the path is the action name** (source `http-server-adapter.ts`):

| Request path (`path: "/"`) | Action |
| --- | --- |
| `GET /` | Health probe, returns `{ "status":"ok","retcode":0,"data":{"online":true} }` |
| `POST /send_group_msg` | `send_group_msg` |
| `POST /get_group_list` | `get_group_list` |
| `GET /_events` | SSE event stream (requires `enableSse: true`) |

With `path: "/onebot"`, action paths become `/onebot/send_group_msg`.

A path outside that prefix returns:

```json
{ "status": "failed", "retcode": 1404, "data": null, "wording": "not found" }
```

### 5.2 Three request styles

**① Action in the path + JSON body (most common)**

```bash
curl -X POST http://127.0.0.1:3000/send_group_msg \
  -H 'Authorization: Bearer REPLACE_WITH_YOUR_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"group_id":20001,"message":[{"type":"text","data":{"text":"你好"}}]}'
```

**② `action` embedded in the JSON body**

```bash
curl -X POST http://127.0.0.1:3000/ \
  -H 'Authorization: Bearer REPLACE_WITH_YOUR_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"action":"send_group_msg","params":{"group_id":20001,"message":"hi"},"echo":"req-1"}'
```

**③ GET + query parameters**

```bash
curl -G http://127.0.0.1:3000/get_group_member_info \
  -H 'Authorization: Bearer REPLACE_WITH_YOUR_TOKEN' \
  --data-urlencode 'group_id=20001' --data-urlencode 'user_id=10001'
```

POST with `application/x-www-form-urlencoded` is also supported.

Query and form parameters are each **tried with `JSON.parse`**, falling back to the raw string on failure,
so both `?user_id=10001` and `?user_id="10001"` parse to a number.

### 5.3 `echo` reflection

When the request carries `echo`, the response **echoes that field back unchanged** (source `if (echo !== void 0) response.echo = echo;`),
which makes asynchronous concurrency easier to match up.

### 5.4 Methods and errors

> ⚠️ **Action-level failures still return HTTP `200`**.
> `retcode 100/1400/1404/1200` all appear inside a response body with **HTTP 200**.
> Judge success by `retcode`, not by the HTTP status code alone.

| Situation | HTTP | retcode | wording |
| --- | --- | --- | --- |
| Action succeeded | `200` | `0` | — |
| Parameter validation failed | **`200`** | `1400` | e.g. `group_id is required` |
| Action execution failed | **`200`** | `100` | Specific reason |
| Action does not exist | **`200`** | `1404` | `unknown action` |
| Not GET/POST | `405` | `1400` | `method not allowed` |
| Missing `action` | `400` | `1400` | `bad request: missing action` |
| JSON syntax error | `400` | `1400` | `bad request: invalid json` |
| Unsupported Content-Type | `400` | `1400` | `bad request: unsupported content-type: ...` |
| Request body too large | `413` | `1413` | — |
| Internal exception | `500` | `1200` | Exception details |
| Server shutting down | `503` | `1200` | `server closing` |
| Unauthorized | `401` | `1401` | `unauthorized` |
| Path outside the `path` prefix | `404` | `1404` | `not found` |

## 6. WebSocket access in detail

### 6.1 The three roles

`role` determines **what that connection sends and receives** (source `ws-server-connections.ts` /
`ws-client-adapter.ts`):

| role | Receives events | Accepts action requests |
| --- | --- | --- |
| `Api` | ✗ | ✔ |
| `Event` | ✔ | ✗ |
| `Universal` | ✔ | ✔ |

- Events are pushed only to `Event` / `Universal` connections.
- Action requests are accepted only from inbound messages on `Api` / `Universal` connections.
- Action requests sent on an `Event` connection are **ignored** (without an error).

### 6.2 Path classification (forward WS)

When `path` is `"/"` and `role` is `Universal`, the role can be distinguished by **subpath**:

| Path | Resolved role |
| --- | --- |
| `/` | `Universal` |
| `/api` | `Api` |
| `/event` | `Event` |

Ending in `/api` → `Api`; ending in `/event` → `Event`; anything else → `Universal`.
A path that does not match the configuration rejects the handshake (`400 Bad path for WebSocket`).

### 6.3 Handshake headers in both directions

**Reverse WS (`wsClients`, Haizakura as client)** sends:

```
User-Agent: OneBot/11
X-Self-ID: <uin>
X-Client-Role: Universal | Api | Event
Authorization: Bearer <accessToken>     # 仅在配置了 token 时
```

**Reverse HTTP (`httpClients`)** sends:

```
Content-Type: application/json
User-Agent: OneBot
X-Self-ID: <uin>
X-Signature: sha1=<HMAC-SHA1(accessToken, 原始body) 的 hex>
```

### 6.4 Heartbeat and reconnection

**Server → client (meta events)**: `OneBotInstance.HEARTBEAT_INTERVAL = 30000` ms,
pushing a `meta_event` / `heartbeat` every 30 seconds (see `events.md` for details).

**Liveness probing for reverse WS**: `HEARTBEAT_INTERVAL_MS = 30000`,
`HEARTBEAT_MAX_MISSED = 2`, meaning about **90 seconds** without an inbound response marks the connection
half-open and reconnects (`HEARTBEAT_DEAD_AFTER_S = 30 * 3 / 1000`).

**Reconnect interval**: `reconnectIntervalMs`, default `5000`, minimum `1000`.

### 6.5 Reverse WS sends meta events first on connect

Once the connection is established the server immediately pushes bootstrap meta events (lifecycle and so on),
and only afterwards pushes incremental events. Clients should tolerate "receiving a meta_event right after connecting".

## 7. SSE access in detail

### 7.1 Enabling and the address

```json
{ "name": "main", "host": "0.0.0.0", "port": 3000, "enableSse": true }
```

The event stream address is **`GET <path>/_events`** (`/_events` when `path` is `/`).

Accessing it while disabled returns:

```json
{ "status": "failed", "retcode": 1404, "data": null, "wording": "SSE is disabled" }
```

A non-GET method returns `405` + `retcode 1405` + `wording: "SSE requires GET"`.

### 7.2 Response headers and frame format

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
Connection: keep-alive
```

Once connected it first sends `retry: 3000`, then each frame:

```
id: <epoch-uuid>:<sequence>
data: <事件 JSON>

```

Every **15 seconds** it sends a comment line `: ping` as a keepalive.

### 7.3 Reconnection and `Last-Event-ID`

A client may send `Last-Event-ID: <epoch>:<sequence>` when reconnecting to request replay:

| Situation | Response |
| --- | --- |
| Malformed value | `400` `invalid Last-Event-ID` |
| Epoch mismatch / sequence out of range / already discarded | `409` `SSE replay unavailable; resync and reconnect without Last-Event-ID` |

On `409`, **clear `Last-Event-ID` and reconnect**, rebuilding from the current state.

### 7.4 Buffer limit

If a single connection accumulates more than **8 MiB** (`CLIENT_BYTES = 8 * 1024 * 1024`) it is **actively
disconnected**, with the log message `SSE client exceeded N buffered bytes; disconnecting`.
Slow consumers should switch to WebSocket or paginated fetching.

## 8. Message format: `array` vs `string`

Each adapter's `messageFormat` determines the shape of the **`message` field in events**:

| Value | `message` field | Description |
| --- | --- | --- |
| `"array"` (default) | Message segment array | Structured; recommended |
| `"string"` | CQ code string | Takes the value of `raw_message` |

Source `event-filter.ts`:

```js
function shapeEventForAdapter(event, options) {
  if (event.post_type === "message_sent" && !options.reportSelfMessage) return null;
  if (options.messageFormat === "string"
      && (event.post_type === "message" || event.post_type === "message_sent")
      && Array.isArray(event.message)) {
    const raw = typeof event.raw_message === "string" ? event.raw_message : "";
    return { ...event, message: raw };
  }
  return event;
}
```

Note that only **message-category events** are affected; when `reportSelfMessage: false`,
`message_sent` (messages you sent) causes **the entire event to be dropped**.

**The send direction is not constrained by `messageFormat`**: the `message` parameter accepts an array,
a CQ code string (`[CQ:face,id=1]`) or an object, parsed by `parseMessage`.
With `auto_escape: true`, CQ codes in the string are **not parsed** and are sent as plain text.

### 8.1 Segment types

**Receive direction** (element → segment; `ELEMENT_CODECS` in `element-codecs.ts`, **16** in total):

```
text  face  at  reply  image  record  video  json  xml
file  mface  poke  flash_file  forward  markdown  inline_keyboard
```

**The send direction** accepts 9 additional **compatibility segments** that are converted into the elements above
(`segmentToElement` in `message-parser.ts`):

```
node  share  music  location  contact  rps  dice  shake  anonymous
```

> `node` is only allowed inside a **merged forward** (forward node list);
> using it at the top level reports `UNSENDABLE_TYPE`.
> `share` / `music` are converted into `json` cards; `music`'s `custom` type
> needs an external signing service (default `https://ss.xingzhige.com/music_card/card`).

**Empty text placeholder rule** (source `isExplicitEmptyTextPlaceholder`):
a text segment whose `text` field is **exactly the empty string `""`** is treated as a **compatibility placeholder**
and does not count as a "sendable segment"; whereas a field that is **missing / `null` / whitespace only** still goes through normal validation.

## 10. Common problems

| Symptom | Cause | Fix |
| --- | --- | --- |
| `retcode 1401 unauthorized` | Token mismatch or not sent | Check `Authorization: Bearer` |
| `retcode 1404 not found` | Path outside the `path` prefix | Verify the `path` configuration |
| `1404` + `SSE is disabled` | `enableSse` not enabled | Enable the switch and reload |
| WS handshake `400 Bad path` | Path does not match the `path`/role rules | See §6.2 |
| No events received | The connection's role is `Api` | Switch to `Event` / `Universal` |
| Your own messages are not pushed | `reportSelfMessage: false` | Set it to `true` |
| The port does not take effect | Entries with `port <= 0` are dropped | Use a valid port (1–65535) |
| Configuration has no effect | The filename is not `onebot_<digits>.json` | See §2.1 |
| `message` in events is a string | `messageFormat: "string"` | Change it to `"array"` |
