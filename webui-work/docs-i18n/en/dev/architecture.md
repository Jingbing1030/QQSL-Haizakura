# Developer documentation


Monorepo structure, core startup path and contribution notes

Haizakura is a mixed TypeScript + native module project. TypeScript handles runtime orchestration, the OneBot implementation, protocol bridging, the SDK and the WebUI; native modules provide Hook, injection and high-performance WebSocket capabilities.

## Monorepo structure

A pnpm workspace with 5 packages:

```
Haizakura/
├─ packages/
│  ├─ core/        @snowluma/core       核心：Bridge / OneBot / Hook
│  ├─ websocket/   @snowluma/websocket  本仓内置 WS 实现（依赖原生 addon）
│  ├─ sdk/         @snowluma/sdk        外部消费者用的 TS OneBot 客户端
│  ├─ webui/       webui                React + Vite 控制台
│  └─ runtime/     运行时发行模板（启动脚本 / launcher / package.json）
├─ native/         平台原生产物（.node / .dll / .so）
├─ dist/           构建输出
├─ tools/          辅助脚本（version bump、release 等）
├─ docs/           ADR 等开发文档
└─ package.json
```

## Core startup path

The entry point is `packages/core/src/index.ts`:

```
loadRuntimeConfig()           ← 读 config/runtime.json / env
  ↓
HookManager(autoLoadOnDiscovery)
  ↓
BridgeManager
  ↓
OneBotManager                 ← 按 UIN 拉起 OneBotInstance
  ↓
initWebUI(port=webuiPort)     ← 仅完整构建启用
```

Created at startup:

- `HookManager` — discovers the main QQ process and injects the native addon; with `hookAutoLoad: true` it injects automatically for every newly discovered PID.

- `BridgeManager` — decodes Hook messages from the named pipe into bridge events; caches rkey / contacts / group members.

- `OneBotManager` — creates one `OneBotInstance` per UIN; owns `MessageStore` / `MediaStore` / `NetworkManager`.

- `initWebUI` — starts the WebUI in full builds; the port defaults to `5099` (configurable via `runtime.json.webuiPort`).

## Hook and native modules

The Hook native module is loaded through `process.dlopen()`. Its source lives in the separate `dev/nnphook` repository.

Platform naming convention:

```
snowluma-win32-x64.node    snowluma-win32-x64.dll
snowluma-linux-x64.node    snowluma-linux-x64.so
snowluma-linux-arm64.node  snowluma-linux-arm64.so
```

Load search paths:

```
native/
dist/native/
packages/runtime/native/
```

The native addon exposes:

- `getAllMainProcess` — enumerates main QQ processes.

- `loadModuleManual` — manually maps an injection module into a target process.

- `unloadModuleManual` — unloads an injected module.

The default target process name is `QQ.exe` on Windows and `qq` on Linux.

## OneBot lifecycle

When the bridge layer detects that a QQ session has started:

- Load `config/onebot_.json` (copying from the global file when missing).

- Construct an `OneBotInstance`.

- Start the HTTP / WS / reverse WS / HTTP POST adapters (per the `networks.*` configuration).

- Asynchronously warm the friend list, group list and group member list.

- Forward bridge events as OneBot events.

The corresponding instance is released when the session closes.

## WebSocket package

`@snowluma/websocket` is the project's own WebSocket implementation, with an interface kept as close to `ws` as possible but with native acceleration.

Exports:

- `WebSocket` — client constructor.

- `WebSocketServer` — server constructor.

- `Server` — an alias of `WebSocketServer`.

- `InternalWebSocket` — internal connection implementation.

It depends on the platform's native `.node`, loaded from the same `native/` search paths.

## SDK package

`@snowluma/sdk` is a fully typed OneBot client for third parties. It can be published to npm independently and does not depend on the Haizakura runtime. It is built inside the monorepo (see `pnpm build:sdk` / `build:all` below); for consumer usage see the SDK documentation.

## Development commands

```
pnpm install
pnpm dev              # core 开发模式
pnpm dev:web          # WebUI 开发服务器
pnpm build            # 仅 core
pnpm build:webui      # 仅 WebUI
pnpm build:sdk        # 仅 SDK
pnpm build:all        # core + SDK + WebUI
pnpm test             # core 测试
pnpm typecheck        # 全仓类型检查
pnpm lint             # 全仓 lint
```

## Build order

For a complete release:

```
pnpm build:all
```

which runs, in order:

- A full `@snowluma/core` build

- `@snowluma/sdk`

- `webui`

Artifacts are all emitted to `dist/`.

## Documentation site

The documentation site lives in the separate `Haizakura/HaizakuraDocs` repository (usually checked out locally to `dev/HaizakuraDocs/`, alongside the main repository).

Stack: Rspress + React + TypeScript + MDX + KaTeX.

The OneBot API reference is generated by the docs repository's `pnpm api:generate` (wired into `prebuild`) from `docs/public/api/catalog.json` — one page per action, plus category overview pages and a searchable catalog landing page. `catalog.json` is the action catalog produced by the main repository's `collectActionDocs()` (isomorphic with `@snowluma/mcp`'s `CatalogAction`), and the main repository's `sync-docs-catalog` workflow commits it automatically to the docs repository at release time using the Haizakura bot — no manual maintenance required.

## Contribution notes

- Do not bypass BridgeManager: the OneBot layer always calls NTQQ capabilities through `BridgeInterface`, which keeps things decoupled and testable.

- Keep configuration auto-generatable: new fields must be backward compatible; normalize on parse and write back to disk.

- Distribute native modules per platform: when adding a platform, ship both the `.node` and the injectable library.

- Prefer adding tests: core OneBot behavior is verified with `vitest`; see `packages/core/tests/`.

- API documentation automation: adding an action with `defineAction` (optionally with `returnsSchema` describing `data`) is enough — `catalog.json` is synchronized automatically by the `sync-docs-catalog` workflow, so the API reference never goes stale; for a local preview run `pnpm api:generate` manually.
