# Plan before V2.0.0


- [x] Unify Uid/Uin behind a single Service with SQLite persistence, so groups, friends, join requests and friend requests all obtain the new Uid.
- [x] Improve the debugging experience with packaging-free debug runs while keeping the data directory correct. (The Proton fallback approach becomes type extraction via ts + map for tsx and nodejs, stripped during normal Vite builds.)
- [x] Split core into Common (shared capabilities), OneBot (outer wrapper and protocol conversion), Core (raw Api and foundational capabilities) and Bridge (wrapping and key decoding, plus Event message/sent group/member_add ...).
- [x] Move Protocol Buffer definitions into a separate package.
- [x] Tidy the send and decode message paths for better performance. `packages/{bridge,onebot}/bench/*.bench.ts` produced baseline numbers. The main bottleneck is not protobuf decoding (already sub-μs) but two places where SQLite repeatedly `db.prepare(sql)`s, re-parsing each time — after switching `node:sqlite` (experimental) to `better-sqlite3` (stable) and caching prepared statements: the full `group_member_join` path went 17.5μs → 4.7μs (**3.7x**), `storeMeta` 17μs → 11μs, `storeEvent` 23μs → 18μs, `findMeta` 5.4μs → 1.3μs (**4x**). The combined send-side hot path (storeMeta + storeEvent) went 40μs → 29μs per message. Also removed the redundant `Buffer.from(pkt.body)` allocation (pkt.body is already a Uint8Array). Secondary optimizations — synchronous fast path in `elementsToJson`, WAL checkpoint tuning, JSON serialization replacement — are left for when there is real throughput pressure.
- [x] Adopt an Api layer aligned with NapCat's design, attached to ctx, in both Core and OneBot.
  - [x] Core side: 13 Api classes (message/contacts/groupAdmin/groupFile/groupAlbum/interaction/friend/profile/forward/misc/extras/web) are attached at `bridge.apis.<area>.method()`, and `BridgeInterface` plus `actions/*` have been removed entirely.
  - [x] OneBot side: `ApiActionContext` dropped ~40 pure forwarding fields (the groupAdmin / groupFile / groupAlbum / friend / interaction / message / profile / web areas), and actions now call Core's Api layer directly via `ctx.bridge.apis.<area>.method(...)`. The ~30 remaining fields are all real composition helpers (module-level send/forward, message store reads, meta-lookup composers). Full NapCat-style structure (class-per-action / TypeBox schema / actionName enum / auto-register decorator) has not been done yet — it waits until profile documentation and toolchain needs appear.
